## 1. 行為真源複核：與 Plan／ACCEPTANCE 不符的發現

### 1.1 【事實錯誤】C-18 與 Plan §4.10 的 isBusy 前提不成立

Plan §4.10 原文：「主防線＝1:1 保留 isBusy 語義（批處理期間禁全部按鈕＋輪詢停，albumChanged 天然不觸發）；縱深＝session ID」。

實際逐行核對（`toggleBusy` 定義 py:406-417，輪詢跳過 py:508-510）：

| 操作 | 是否調 toggleBusy | 實際禁用範圍 | 輪詢 |
|---|---|---|---|
| 載入專輯 `runAlbumBatch` | **是**（py:621 / 639） | 全部 5 個按鈕 | 停 |
| Fetch Missing | **否** | 只禁自己（py:657 / 678） | **照跑** |
| Import All | **否** | 只禁自己（py:723 / 738） | **照跑** |
| Import Selected | **否** | **完全不禁**（py:682-709 無 disabled） | **照跑** |

即：C-18「Batch 作業期間 isBusy：按鈕全禁＋輪詢停」**只對「載入專輯」成立**，對其餘三個操作全不成立。

由此，原版存在三個真實競態窗口（非理論）：

1. Fetch Missing 跑到第 i 首時使用者切專輯 → 輪詢照跑 → `lastAlbum` 變 → `batchData = []`（py:492）→ Batch 可見則 `runAlbumBatch()` 重載 → 舊循環仍在往**已被替換的舊陣列元素**寫 lyrics 並呼叫 `renderBatchTable()`（渲染的是新 `batchData`）→ 進度文案錯亂、命中寫不進列表。
2. Fetch Missing 進行中，Import All 按鈕未禁 → 兩個串行循環交錯寫入。
3. Import Selected 完全無禁用 → 可連點重複寫入（冪等，危害小）。

**結論：session ID 守衛不是「縱深」，是唯一防線。** C-18 需改寫，Plan §4.10 對應句需修正。

### 1.3 【原版缺陷，需裁決】2 條

**(a) `has_lyrics` 與實際渲染語義分裂。** 後端 `get_album_data` 為每首算了 `has_lyrics = bool(lyrics.strip())`（py:2253-2254），但前端**從未使用該欄位**——白點/暗紅點（py:587）、Fetch Missing 篩選（py:651）、Import All 篩選（py:717）三處全部用 `track.lyrics && track.lyrics.length > 0`（未 strip）。

現有 Swift `AlbumTrack.hasLyrics` 用的是 `trimmingCharacters(...).isEmpty` ＝ **跟了那個沒人用的欄位**。

可見分歧（歌詞為純空白如 `"   "` 或 `"\n\n"` 的曲目）：

| | 原版（length>0） | Swift 現狀（trim） |
|---|---|---|
| 狀態點 | 白點（有詞） | 暗紅點（缺詞） |
| Fetch Missing | 跳過 | 會抓 |
| Import All | 會寫入（把空白寫進音樂庫） | 跳過 |

**裁決（用戶 2026-08-14 拍板）**：採 trim 語義——純空白＝缺詞。`AlbumTrack.hasLyrics` 維持現狀不改，Fetch Missing／Import All 的篩選一律走 `hasLyrics`。記為 ⚠️ 偏差 C-29，理由：該分歧源於原版自身的內部不一致（後端算了 `has_lyrics` 卻無人使用），非有意設計；修正方向符合「缺詞才抓詞」的操作意圖，且與已批准的 B-11a／C-10a「原版判定缺陷一律修」精神一致。

**(b) Batch 會把 Genius 錯誤訊息當歌詞。** `fetch_single_missing` 只判 `result.startswith("Error")`（py:2232），而 Genius 異常路徑回傳的是 `"Genius Error: …"`（py:1283-1284）——不以 `Error` 開頭，故**直接 return 當作歌詞**。前端過濾只擋 `No track`／`Lyrics not found` 兩個前綴（py:665），也放行。結果：`"Genius Error: …"` 寫進 `track.lyrics` → 顯示白點 → **Import All 會把這串錯誤訊息寫進音樂檔的 lyrics 欄位**。

與 B-11a（Editor 側同源缺陷，已批准修正）是同一個 bug 的兩個出口。Swift 側 `LyricsResult` 是列舉，`.error` 天然不會被當成 `.found`，等於已隱式修正——但 C 段無對應條目記錄。

## 2. 併發防護方案（基於 §1.1 修正後的前提）

原則：**可觀察行為 1:1，內部競態用守衛兜住。**

- 按鈕禁用範圍逐操作 1:1 照搬（載入＝全禁；Fetch Missing／Import All＝只禁自己；Import Selected＝不禁）。
- **輪詢不停**（原版三操作期間輪詢照跑，Editor 曲目卡會更新，屬可觀察行為）。
- 每次專輯載入生成 `sessionID`；串行循環的每步回寫前校驗 `sessionID` 仍等於當前值，不等則靜默中止該循環（不改狀態文案，避免製造原版沒有的可觀察行為）。
- **載入路徑本身也要守**（2026-08-15 Phase 3 補）：`loadAlbum()` 在 `await` 前捕獲 session、回寫前校驗。擋兩種重疊——(a) 切專輯：`handle()` 已先遞增 sessionID，舊載入回來不得把已切走的專輯填回列表與 header；(b) 同代重入：`tabActivated()` 不碰 sessionID，連點分頁會讓兩個載入捕獲同一 session 值，靠成功路徑的遞增讓先完成者作廢後完成者，只提交一次。
- Import Selected 的重複點擊不阻擋（1:1），寫入本身冪等。

## 7. 實施中的發現（2026-08-14）

### 7.1 xcodegen 不重生成，新檔不進 target——測試會「假綠」

新增 `.swift` 後直接跑 `xcodebuild test`，**回報 TEST SUCCEEDED 但跑的是舊的 126 個測試**——xcodeproj 的檔案清單是靜態的，新檔未被納入編譯，連 `cannot find type` 都不會報。必須先 `xcodegen generate` 再測。

### 7.2 UITest 集體超時的根因＝app 首次啟動慢，非 M6 代碼缺陷

全量測試中 10 個 UITest 全數失敗（連「首屏應為 splash」都失敗），但單元測試 153 全綠。逐層驗證：

| 實驗 | XCUITest "Wait for accessibility to load" | 結果 |
|---|---|---|
| 全量（單測 → UITests） | — | 10/10 失敗 |
| 單跑 1 個（該構建的首次啟動） | **18.87s** | 通過（splash 斷言先吸收了等待） |
| 單獨跑 10 個（已預熱） | **0.42–0.57s** | 10/10 通過 |
| 手動 `open` 啟動 app | — | 視窗 1200×800 正常，無崩潰報告 |

即：新構建的 app 首次啟動需 ~19s 才讓 AX 樹就緒（含 lsregister 註冊與代碼簽名驗證），而 `waitForMainUI` 只等 15s；全量測試中 UITests 緊接單測執行，正好落在該構建的首次啟動上。修復＝把 timeout 提到 45s 並在測試碼註明實測依據。**產品本身啟動正常**，此為測試基礎設施的脆弱性。

排查中一度以為「app 進程活著但無視窗」是真實缺陷——那是我用 `nohup` 直接跑 bundle 內二進位、繞過 LaunchServices 造成的假象，改用 `open` 後視窗正常。教訓：驗證 GUI app 必須走 LaunchServices。

### 7.3 UITests 與單元測試同批執行時不穩定（既有問題，非 M6 引入）

把 timeout 提到 45s 後仍觀察到殘留失敗，逐次記錄：

| 執行方式 | 單元測試 | UITests | 失敗性質 |
|---|---|---|---|
| 全量（重建後首跑） | 156 綠 | 6/10 | 前台焦點：`MenuBarItem is not foreground`、`does not have a process ID`；一次 AX 等待達 56.8s |
| 全量（已預熱） | 156 綠 | 9/10 | `testQuitMenuItemTerminatesApp`：Quit 後 state 仍為 runningBackground |
| 單獨跑該失敗用例 | — | 通過（7.4s） | — |
| 單獨跑 10 個 UITests（第一次） | — | 10/10 綠（72s） | — |
| 單獨跑 10 個 UITests（第二次） | — | 9/10 | 同一個 `testQuitMenuItemTerminatesApp` 再度失敗 |

這 10 個用例**完全不觸及 Batch**（`grep -i batch UITests/` 無結果），且每個單跑都必過——失敗只出現在「連續跑多個用例」時，與是否跟在單元測試後面無關（單獨跑 10 個也復現）。

**根因**：`tearDown` 的 `app.terminate()` 不保證同步完成。前一個用例的實例仍在退出中，下一個用例就 `launch()` 了，兩個實例競爭前台焦點——表現為 `MenuBarItem is not foreground`（點不到菜單）或 `app.state` 讀到殘留實例而回報 `runningBackground`（Quit 用例失敗）。

**處置**：修競態本身，不放寬斷言——`tearDown` 改為等進程真正 `notRunning`（上限 10s）再進下一個用例。`waitForMainUI` 的 timeout 提到 45s 則是針對首次啟動的獨立修復，兩者互不替代。

**修復後驗證**：連跑兩輪 UITests，各 10/10 綠（72.3s／72.1s）。

### 7.4 補 Batch UITests 時踩到的四個 XCUITest 事實（用診斷樹確認，非猜測）

補 C-07／C-15／C-21／C-25 時連續失敗，逐一以 accessibility 樹的實際輸出定位：

| 症狀 | 真因 | 處置 |
|---|---|---|
| `containsLabel` 全數失配 | SwiftUI 的 `Text` 在 macOS AX 樹裡把文字放在 **value**，`label` 為空 | 改比對 `value OR label` |
| 按鈕 `app.buttons["IMPORT ALL"]` 找不到 | ActionButton 的 label 是 `done_all, Import All`——MaterialSymbol 的連字文本混進去了，且隨語言變動 | 加 `accessibilityID`，以 identifier 定位 |
| 加了 identifier 後**全部**用例崩壞，耗時 134s→333s，出現 `does not have a process ID` | `.accessibilityIdentifier(id ?? "")` 給所有按鈕塞了**空字串 identifier**，令元素查詢改按 identifier 比對 | 改用 `OptionalAccessibilityIdentifier`，只在有值時掛 |
| `Timed out while evaluating UI query`（111s 未回應） | `descendants(matching: .any)` 掃全樹；載入 12 首曲目後元素數暴增 | 收窄到 `app.staticTexts` / `sheet.staticTexts` |

另外確認框在 macOS 上是 **sheet**（`label: 'alert'`）而非 dialog，文案落在其 StaticText 的 value，Cancel 需限定在 sheet 內查（畫面上不只一個 "Cancel"）。

### 7.5 A-10 三次失敗的熔斷與根因

`testQuitMenuItemTerminatesApp` 在修過 tearDown 競態後仍第三次失敗，觸發熔斷後改為**直接測量產品行為**：以 `open` 啟動、AppleScript 送 quit、輪詢進程消失——**兩次試驗皆為 0.02s**。產品退出正常，失敗純屬連跑後前台焦點漂移導致菜單點擊靜默落空（與 `MenuBarItem is not foreground` 同源）。處置＝菜單交互前 `app.activate()` 並等 `.runningForeground`。

**全量驗證**：156 單測 ＋ 15 UITests（10 Shell ＋ 5 Batch）一次調用全綠。

### 7.6 C-20 真機驗收：五次受阻後改用「XCUITest 操作＋日誌流證據」

C-20（隱藏視窗不中斷 Batch 任務）連續受阻，逐次記錄與排除：

| 嘗試 | 卡點 | 結論 |
|---|---|---|
| `XCUIApplication.activate()` 重顯視窗 | 視窗沒回來 | activate 只激活行程，不送 `'rapp'`；A-09 早已註明 Dock 點擊無法在 XCUITest 內模擬 |
| 測試內以 `Process` 跑 osascript 送 reopen | 仍沒回來（且我用 `try?` 吞了錯誤） | 測試 runner 送 AE 被 TCC 擋 |
| 第二次跑直接啟動失敗 | 等 45s 無主 UI | 上次以紅鈕隱藏後結束，**saved state 記住「視窗已關閉」**；修法＝`-ApplePersistenceIgnoreState YES` |
| 純 AppleScript AX 驅動 | `entire contents` 不支援 `whose` 子句（-1700） | 點不到 Batch 內的按鈕 |
| 直接測產品行為（獨立實驗） | — | **產品正常**：1 視窗 → 紅鈕 → 0 視窗 → reopen → 1 視窗 |

### 8.3 未結項：重疊載入會提前解除 busy（codex R2／R3 重提，待用戶裁決）

codex 連兩輪提出（皆評 P2）：`loadAlbum()` 的 `defer { setLoadingAlbum(false) }` 在過期路徑上照跑，若舊載入先完成而新載入仍在跑，按鈕會提前重新啟用、輪詢也恢復。

**複核結論：codex 對，我最初的「原版一致」駁回開得太寬。** 分路徑看：

- **tab 連點路徑**：原版一樣（兩次 `runAlbumBatch`，第一次的 `finally` 提前清 busy）→ 1:1 成立。
- **切專輯路徑**：原版**不可能發生**。原版的專輯變更由輪詢偵測，而輪詢在 `isBusy` 時跳過（py:508-510）；第一次 `runAlbumBatch` 已 `toggleBusy(true)`，載入期間偵測不到變更，第二次載入無從發起。Swift 的 `onBusyChange` 經 `Task { await monitor.setBusy(...) }` 異步跳板，存在原版沒有的空窗 → **該窗口違反已簽署的 C-18**（載入專輯期間全禁＋輪詢停）。

**未落地的原因（熔斷）**：擬定的修法是把 `isLoadingAlbum` 改為在飛請求計數（`loadsInFlight`，歸零才落下 busy），需配一條重疊載入的測試。該測試連續三次讓單元 target 報 `The test runner hung before establishing connection`（0 條測試執行）；以 `-skip-testing` 排除該用例後單元 target 恢復 150 全綠，證實destabiliser 就是它。依核心協議三次熔斷，停手並把該用例與配套的 `LyricsGate` 多等待者改動一併撤回，工作樹保持在已驗證的綠燈狀態。

**待裁決**：(a) 接受此偏差（影響僅限重疊窗口內的按鈕啟用狀態，資料正確性由 sessionID 保障），或 (b) 另開一輪專門處理，先查清該測試為何掛死 host 進程。

**用戶裁決（2026-08-15）：選 (b)**，於下一個 session 開場執行。屆時的起點事實：
- 撤回前的用例內容見本次 commit 之前的對話記錄；重點是它用同一個 `LyricsGate` 製造兩個等待者，並以 `Task.yield()` ×100 讓第二個載入進場。
- 已證實：`-skip-testing` 排除該用例後單元 target 恢復 150 全綠（三次一致），故 destabiliser 確為該用例本身，非環境。
- 尚未查清：為何它讓 host 進程失聯（`runner hung before establishing connection`，0 條執行）而非單純用例失敗。下探方向＝`MockMusicClient` 的 script 在第二次 `currentTrack()` 已耗盡（`next()` 回 `.notPlaying`）時的路徑，以及 `CheckedContinuation` 是否被洩漏／重複 resume（會 fatalError 直接殺掉 host）。

## 2. 任務清單（每項帶 DoD）

### A1 — 根因定位：重疊載入測試掛死 host（**最先執行，診斷不得污染現場**）

**背景事實**（上游 §8.3 記錄，非本次推測）：
- 撤回的用例用**同一個 `LyricsGate` 製造兩個等待者**，並以 `Task.yield()` ×100 讓第二個載入進場。
- 已證實：`-skip-testing` 排除該用例後單元 target 恢復全綠（三次一致）→ destabiliser 是用例本身，非環境。
- 未查清：為何是 host 失聯（0 條執行）而非普通用例失敗。

**排序修訂（Codex #2 採納）**：原草案把 A2（修 `LyricsGate`）排在 A1 之前，理由「A1 的前置依賴」——此為**診斷污染**：先修了嫌疑對象再去查它是不是凶手，之後即使不再掛死也無法證明原始根因。改為 A1 先行，且**不得改動 `Tests/Support/StubLyricsSource.swift`**；復現直接使用**當前未修改的 `LyricsGate`**——它本身就是單槽位，即原始現場，無需任何替身。

> **實施中修訂（2026-08-23，留痕）**：草案原寫「由測試檔內的局部替身 `BrokenGate` 提供多等待者能力」。實施時發現多餘：當前 `LyricsGate` 已是單槽，直接用它才是最忠實的現場復現。`BrokenGate` 只在 A2 改完（`LyricsGate` 變 broadcast）之後、若仍需復現舊語義時才有必要。此修訂不動驗收標準。

**故障層級（取代原互斥假設 H1–H5；Codex #1 採納）**——自底向上，每層列可觀測預測與排除條件：

| 層 | 內容 | 可觀測預測 | 排除條件 |
|---|---|---|---|
| L1 runner／host | 測試並行化、test host 啟動／連線 | `-only-testing` 尚未建立連線即卡住；0 條執行 | 見下方 H4 判準 |
| L2 Task／actor 調度 | MainActor 死鎖；未捕捉 Task 阻塞 run 收束 | timeout 到期但 host PID 仍存活 | 掛起者可由 os_log 標記定位 |
| L3 測試替身生命週期 | continuation 洩漏（單槽覆蓋）／重複 resume | 洩漏＝`SWIFT TASK CONTINUATION MISUSE` 告警不致命；重複 resume＝`fatalError`／SIGTRAP 殺 host | 當前 `open()` resume 後即清 nil，重複 resume **不可達**（Codex #1 指出，已核實 `StubLyricsSource.swift:32-36`） |
| L4 測試資料腳本 | `currentTrack()` 腳本耗盡後的 `.notPlaying` 路徑（**精確表述**，Codex #4 修改採納：`next()` 確為 `currentTrack()` 內部實作，非錯位；`albumTracks()` 不消耗腳本，故影響僅限此一路徑） | `currentTrackCalls` 無界增長 | 加最大調用次數斷言 |

**症狀三分法（Codex #3 追加，採納）**——每次實驗必須把結果歸入其一，不得混談：
- timeout 到期、host／runner 仍存活 → **測試掛起**（L2／L3 洩漏）
- crash report／SIGTRAP／host PID 消失 → **進程死亡**（L3 重複 resume）
- 未建立測試連線即卡住 → **test host 啟動／連線層**（L1），不得歸入 assertion failure

**驗證步驟**：
1. 在當前已歸零（`parallelizable = "NO"`）工作樹上，以局部 `BrokenGate` 重建最小復現用例，單獨 `-only-testing` 跑，外部 `timeout.sh` 包裹，記錄 stdout／stderr／`~/Library/Logs/DiagnosticReports/` crash report／host PID 存活狀態。
2. **重複判準（Codex #3 複審追加，採納）**：NO 格至少重跑 3 次。
   - 3 次均復現 → **H4（並行化導致）砍掉**，進入 L2／L3／L4 下探。
   - 3 次均不復現 → 改 `project.yml` 為 `parallelizable: true`、`xcodegen generate`、YES 格同樣重跑 3 次；**唯有 YES 穩定復現且 NO 穩定不復現**，才可判 H4 成立。實驗畢須還原 `project.yml` 與 scheme。
   - 3 次結果不一致 → 判為非決定性競態，記錄後按 L2／L3 下探，不得據此下 H4 結論。
3. 依症狀三分法的歸類下探對應層。
4. **三次熔斷**：同一目標連續 3 次實驗無進展 → 停手重建事實表，執行 §6 的 A1 熔斷對策。

**DoD**：根因寫成一句話 ＋ 至少一條命令輸出為證；四個故障層各有明確「砍掉」或「證實」判定；症狀已歸入三分法之一；根因與證據寫入本 Plan 附錄；復現用例（`Tests/Features/A1ReproTests.swift`）於 A1 結案後刪除或改造為回歸用例。

### A2 — `LyricsGate` 支持多等待者（**A1 出結論後才動**）

**改動**：`private var continuation:` 單一槽位 → `private var waiters: [CheckedContinuation<Void, Never>]`；`open()` 遍歷 resume 後清空。保留 `isOpen` 早退語義。

**語義聲明（Codex #8 修改採納）**：保留 `LyricsGate` 名稱（改名波及 C-02／C-09／C-19／C-27 四組調用點，收益不抵風險），但在型別文檔註釋中**明文定義**：`open()` 是 **broadcast**——一次放行**全部**等待者，非單一令牌。需要單一放行語義的未來測試必須另建型別。

**DoD**（Codex #8／#9 採納）：
- `gateResumesAllWaiters`：兩個等待者，`open()` 後兩者皆推進。
- `gateReturnsImmediatelyAfterOpen`：已 open 後再 `wait()` 立即返回。
- `repeatedOpenDoesNotDoubleResume`：重複 `open()` 不重放（防 `fatalError`）。
- `cancelledWaiterDoesNotHangGate`：等待中 Task 被取消後 `open()` 仍正常放行其餘等待者。（**範圍限定**：僅加此斷言與註釋說明取消語義，不實作完整可取消等待機制——此替身僅供測試，完整實作屬投機性泛化。）
- 既有 C-02／C-09／C-19／C-27 對應用例**逐條**確認仍綠。

### A3 — 修 C-18 偏差：`loadsInFlight` 在飛請求計數

**問題**（上游 §8.3 複核結論，codex 勝方意見）：
- tab 連點路徑：原版一樣提前清 busy → 1:1 成立，**不改**。
- 切專輯路徑：原版**不可能發生**（輪詢在 `isBusy` 時跳過 py:508-510，載入期間偵測不到專輯變更）。Swift 的 `onBusyChange` 經 `Task { await monitor.setBusy(...) }` **異步跳板**，存在原版沒有的空窗 → 違反已簽署的 C-18。

**方案選定**：`loadsInFlight` 計數。**已駁回** Codex #5 建議的「generation token 取消／取代舊 load」——它會讓第二次載入不發 AE 請求，偏離原版（上游 §8.2 駁回項 1 已裁定 tab 連點重疊載入是原版可觀察行為，屬用戶既裁定）。Codex 複審已接受此駁回。

```swift
private var loadsInFlight = 0
private func setLoadingAlbum(_ loading: Bool) {
    loadsInFlight += loading ? 1 : -1
    let busy = loadsInFlight > 0
    guard busy != isLoadingAlbum else { return }
    isLoadingAlbum = busy
    onBusyChange?(busy)
}
```

**不變量（Codex #5 修改採納，複審再確認）**：`loadsInFlight == 活躍 loadAlbum 呼叫數`。

**DoD**：
- 先寫 RED 測試 `overlappingLoadKeepsBusyUntilLastCompletes`，改動前**必須實測失敗**（失敗輸出留檔於 scratchpad）。
- 不變量測試四條：①每個 `loadAlbum()` 恰好加一次減一次；②任一時點不得小於零；③舊 task 被 `loadTask` 覆蓋**不代表**舊 task 被取消（其計數仍須配對）；④最後一個 load 完成後才發出**唯一一次** `onBusyChange(false)`。
- **整合層測試**（Codex #7 採納）`overlappingLoadSuspendsPollingUntilLastCompletes`：兩個重疊 load 期間驅動 `NowPlayingMonitor.tick()`，斷言整個 busy 區間內 `MockMusicClient.currentTrackCalls` 不增長，末個 load 完成後才恢復。理由：只斷言 `isLoadingAlbum` 與 callback 會因異步跳板而「測試綠但實際仍有 polling window」。
- 全部既有測試保持綠；ACCEPTANCE C-18 狀態說明更新。

### A3b — `NowPlayingMonitor` busy 來源聚合（Codex #6 採納，**附可達性前置**）

**問題**：`AppModel.swift:66` 與 `:76` 兩處分別把 Editor 與 Batch 的 busy 以裸布林寫入 monitor 的**單一** `isBusy`（`NowPlayingMonitor.swift:70-72`）。一方送 `false` 會清掉另一方仍需維持的 busy。

**前置閘門**：先寫測試**證明該交錯可達**（Editor 抓詞中 Batch 載入完成 → monitor 提前恢復輪詢）。
- 可達 → 修。
- 不可達 → **不修**，記錄為理論缺陷寫入附錄，避免無證據的擴大範圍。

> **實施結果（2026-08-23）**：可達性已證實——RED 測試實測 `currentTrackCalls` 由 1 漲到 2，
> 即 Batch 載入完成後 Editor 仍在抓詞但輪詢已恢復。
>
> **落地方式與草案不同（留痕）**：草案寫「`AppModel` 聚合 `editorBusy`／`batchBusy`」，
> Phase 3 的 altitude 審查指出這是把記帳責任上浮到組裝根、形成兩本帳，而同一份 diff 裡的
> `loadsInFlight` 剛用「狀態擁有者自己維護」修過同一 bug class（且 Codex #6 原話也偏好此法）。
> 改為 `NowPlayingMonitor` 自己維護 `busySources: Set<BusySource>`，`setBusy(_:source:)` 顯式帶來源；
> `AppModel` 的三樣聚合狀態全部消除。M7 新增來源只需擴 `BusySource` 列舉，不必動 `AppModel`。

**DoD**：可達性測試有明確結論（RED 輸出或「不可達」的推理鏈＋證據）；若修，交錯序列測試綠；不擴大到重寫 monitor 的 busy 模型。

## 附錄 A1：根因結論（2026-08-23 實驗結果）

### 症狀 1：`The test runner hung before establishing connection`（0 條執行）

**根因（一句話）**：test host app 啟動時讀 Keychain 的 `GENIUS_ACCESS_TOKEN`，而 app 為 ad-hoc 簽名，

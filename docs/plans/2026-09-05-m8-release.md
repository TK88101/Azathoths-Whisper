## 1. 目標與非目標

1. 圖標接線（Finder／Dock／DMG／關於窗顯示正確圖標）。

## 2. 任務清單

### A 欄：我可獨立完成並自證

#### M8-1 圖標接線（**loose icns 路線**）
`cp MyIcon.icns AzathothsWhisper/Resources/AppIcon.icns` ＋ `project.yml` 的 `info.properties` 加 `CFBundleIconFile: AppIcon`。
**不建 `Assets.xcassets`**：`MyIcon.icns` 與 `MyIcon.iconset/` 由 `make_icns.py`＋`iconutil` 從同一組 PNG 產出，
shipping 像素完全一致；asset catalog 路線要手寫 11 個 `Contents.json`、加 build setting，
且該 setting 若加在頂層 `settings.base` 會污染兩個測試 target（actool 找不到 icon set 產生噪聲 warning）。
asset catalog 只有在 App Store 上架或要支援 macOS 26 圖標變體時才必要——兩者都在非目標裡。

**DoD**（全部為「具體值＝預期值」）：
1. **產物 `Contents/Resources/AppIcon.icns` 與倉庫源 `MyIcon.icns` 逐字節相同**（`cmp`）——
   證明出貨的就是 1.x 那個圖標本身、Xcode 未對 loose resource 重編碼。
   ＋ `iconutil -c iconset` 解包後**十槽尺寸齊全**（16/32/64/128/256/512/1024 全覆蓋）。
   **更正（實施時發現）**：本條原寫「解包後逐槽 `shasum` 與 `MyIcon.iconset/` 相同」，
   該判據**設計錯誤**——icns 是容器格式，`iconutil` 解包會對部分槽重編碼，
   字節級往返本就不保證（實測 16/32/1024 三槽字節不同、尺寸全對，
   歸一化後仍差 1–205 字節）。解包結果不是出貨內容，拿它當判據會製造假失敗。
2. `PlistBuddy -c "Print :CFBundleIconFile"` 讀出 `AppIcon`。
3. `xcodegen generate && git diff --exit-code AzathothsWhisper/App/Info.plist` —— 幂等，鍵未被抹除。
4. Finder 截圖**前**先 `killall Finder` 清圖標快取（否則同路徑舊 bundle 的陳舊圖標會讓截圖假通過）；
   截圖只作輔助，判定以第 1 項為準。

#### M8-3 H-04 的兩半拆分（**不寫新測試**）
- **調度層「不無界餓死」**：引用既有 `ArtworkAEFairnessTests.monitorCallWaitsBehindAtMostOneArtworkDuringPrefetch`。
- **1.5s 時間界**：**該測試自己聲明不覆蓋**（`:11-14`）。ACCEPTANCE H-04 必須**明寫**：
  「單測只覆蓋調度層不餓死；`SBApplication.timeout` 的實際生效屬真機驗（M8-13）」。

  2. **層次不可達**：饑餓發生在 `MusicAppleEventsClient` 的 AE 串行化上，而 monitor 的

#### M8-12 乾淨機 checklist（十步，可證偽形態）

**第 1 步只有一條路：新建一個 macOS 使用者帳號。**

理由不是「更安全」，是**唯一可行**（此論證由過度設計評審者在複審中給出，比原理由更硬，我已復核）：
`SecretStore.swift:19` 的 `KeychainStore` service 預設值硬編碼為 `com.ibridgezhao.azathothswhisper`，
**2.0 寫的是與 1.x 同一條 Keychain 項**。因此在主帳號上：
- 就算第 1 步不刪 token，**第 8 步存值時照樣會覆蓋掉它**；
- 就算第 8 步改用哨兵值，被覆蓋的仍是那條真項。

要保住 token 就得「第 1 步備份 → 第 8 步覆蓋 → 跑完恢復」，兩次進出真 Keychain，
比新建帳號複雜且風險面更大。**乾淨帳號是唯一能讓第 8／9 步完全不碰真 token 的路線。**

**備選路線（僅在你明確選擇時走，且屬破壞性操作需逐條確認）**：
```bash
umask 077
security find-generic-password -w -s com.ibridgezhao.azathothswhisper -a <key> > ~/azw-token.bak
defaults export com.ibridgezhao.azathothswhisper ~/azw-prefs.bak.plist
mv ~/.azathoths_whisper_config{,.bak}
tccutil reset AppleEvents com.ibridgezhao.azathothswhisper
# 恢復後立刻：rm -P ~/azw-token.bak
```
**硬約束**：備份／恢復兩步是**使用者獨佔步驟**——agent 不得執行、不得讀取該檔案、
不得在報告或證據包中引用其內容。`-w` 會把 token 明文送到 stdout，
若無重定向與 `umask 077` 就等於為了防「不可逆刪除」開了一個「不可逆洩漏」的口子
（同 memory `no-credential-fields-in-ui-screenshots` 的類別，另撞全局 §7「絕不粘貼密鑰」）。

## 4. 測試策略

- M8-4 是測試代碼，先 RED 後 GREEN。
- 打包配置無「先寫失敗測試」形態 → 以**產物斷言**替代，每項配置改動配一條可執行檢查（見各 DoD）。
- 每次改 `project.yml` 後必跑 `xcodegen generate` ＋ 全量單元測試（M6 教訓：新檔未經 xcodegen 會靜默不編譯）。
- **已知 flaky（2026-09-05 實測復現，修正本檔早先的錯誤結論）**：
  `BatchOverlappingLoadTests/overlappingLoadSuspendsPollingUntilLastCompletes()`
  在 HEAD `cc88a53` 上**全量跑會掛起**。
  **本檔一度寫「當前不復現」，那是錯的**——當時連跑三次全綠只是撞上了 flaky 的好運那一面。
  後續同一命令復現兩次，形態為
  `Test run with 220 tests in 28 suites passed`（掛起前跑完的那批）＋ `** TEST FAILED **`，
  總耗時 138.9s，`Failing tests:` 明確指名該用例。
  **超時上界是把真相逼出來的那一步**：沒有
  `-test-timeouts-enabled YES -default-test-execution-time-allowance 120`，
  這次就是一次永久掛起（M6 `kill -9 testmanagerd` 事故的起點），而不是一條指名道姓的失敗。
  這條標誌**由紅隊評審提出、我方一度以「實測通過」為由駁回其強制 skip 主張、
  評審者又因自己兩次跑通而撤回**——雙方都被同一個 flaky 騙過，最後靠它自己建議的超時上界翻案。
- **跑全量單測的標準命令**（本檔所有 V1／V2 判定均以此為準）：
  ```bash
  xcodebuild test -project AzathothsWhisper.xcodeproj -scheme AzathothsWhisper \
    -destination 'platform=macOS' -only-testing:AzathothsWhisperTests \
    -skip-testing:"AzathothsWhisperTests/BatchOverlappingLoadTests/overlappingLoadSuspendsPollingUntilLastCompletes()" \
    -test-timeouts-enabled YES -default-test-execution-time-allowance 120
  ```
  **括號不可省**（不帶括號時過濾靜默失效，該測試照跑）。加 skip 後 **304 tests / 34 suites 全綠，3.35s**。
  該用例本身已熔斷，不重啟調查；但**每次跑都必須帶超時上界**，讓它萬一從 skip 名單漏掉時以有界失敗暴露。
- 覆蓋率應維持 ≥87%（M7 P2 水位）；下降 → 查是否誤刪測試。

- **實施中觀察到一次間歇性紅燈（2026-09-05，已記錄未查清）**：
  同一條 `-only-testing:AzathothsWhisperTests` 命令回報
  `Test run with 220 tests in 28 suites passed` ＋ `** TEST FAILED **`。
  `220/28` 是 **M7 P2 之前的舊基線數字**，當次跑的顯然是舊的測試 bundle；
  且「220 passed 但整體 FAILED」的組合指向**某個 target 編譯失敗**
  （scheme 含 UITests target，即使 `-only-testing` 排除它，它仍會被編譯）。
  **緊接著同一命令連跑三次均 `305 tests in 34 suites` 全綠、exit=0、無失敗用例。**
  推測（未證實）：增量構建在新增測試檔後的一次狀態不一致。
  **處置**：記錄在案，不追查（非產品缺陷、不可穩定復現）；
  但它印證了 §4 那條紀律的價值——**測試數字必須逐次看**，
  只看 `TEST SUCCEEDED` 而不看條數，這次就會把「跑了舊 bundle」當成綠燈放過去。

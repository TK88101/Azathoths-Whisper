## 2. 三次失敗記錄（**勿重蹈**）

| # | 方案 | 單測結果 | 真機目視 | 失敗原因 |
|---|---|---|---|---|
| 1 | zIndex 改用 `onGeometryChange` 反算的幾何中心索引 | 綠 | 右邊那張壓住中心（方向與原缺陷相反） | 未查明；`visualCenterIndex` 更新有延遲 |
| 2 | `anchor` 改 `.leading` | EDGE 七點全綠、resize 全綠、runtime 全綠 | 右半屏整片空白、封面擠左、標籤與畫面不符 | **anchor 同時決定 command（設 centerID→滾過去）與 observed（手滑→回寫 centerID）兩個方向**；`.leading` 修好前者卻破壞後者 |
| 3 | `ScrollViewReader.scrollTo` 解耦（observed 留 `.scrollPosition(.center)`，command 走 scrollTo）＋ `.task` 補初始路徑 | EDGE 七點＋RUNTIME 三點全綠，全量 307 tests 綠 | 仍完全沒好，封面偏到一側、位置錯亂 | `onChange → scrollTo` 與使用者手滑打架：守衛 `target != visualCenterIndex` 依賴 `visualCenterIndex`，而它由 `onGeometryChange` 驅動、更新有延遲 → 守衛判空 → 強行 scrollTo 撞上滑動慣性 |

## 3. Codex 裁決（2026-09-09，第六輪）

1. **缺陷 2／3 維持為 2.0 發布阻塞**。三次失敗只推翻了「靠單元測試猜 patch」的方法，
   沒有降低缺陷影響。缺陷 3「最後三項不可達」不能歸類為純觀感問題。
2. **H-02 應新增第四種狀態 ❌「已驗失敗」**——現在它不是「未驗」而是「已驗且失敗」，
   標 ⬜ 不準確、標 ✅ 不誠實。M8 收口條件改為「無 ⬜、無 ❌，所有 ⚠️ 已簽字」。
3. 若最終仍要發布，誠實路徑是**建立有日期與簽字的發布例外決策**，
   把兩項標為 `⚠️ accepted deviation` 並寫明可見症狀、影響範圍、2.0.1 修復目標，
   明說「原 V9 的 H-02 要求被此決策部分取代」。**這是變更驗收基線，不是通過原門檻**；
   release notes 只是披露，代替不了驗收裁決。
4. **H-05 的綠燈很可能是假綠**（比原議題更嚴重）：
   `CoverFlowViewModel.swift:232` 設完 centerID 後**立即**清掉 `isCenteringProgrammatically`，
   而真正的 ScrollView 回呼發生在後續 frame——守衛在需要它的時刻已不存在。
   `CoverFlowViewModelTests.swift:260` 已明文承認此限制，H-05 仍標綠＝證據表過度宣稱。
   **無論走哪條路，H-05 都應從 ✅ 降為「邏輯層通過、交互整合未驗」。**
5. **方法論問題（四點）**：①把雙向 binding 當成帶來源的事件（`.scrollPosition` 只有值沒有來源）；
   ②一個 `centerID` 承擔 command／observed／zIndex／標籤／預取／override 六種角色；
   ③測了落定值，沒測狀態轉移（故障發生在 scrolling／decelerating／settling 跨幀期間）；
   ④已有測試明知斷言的是錯誤行為，卻仍標綠。

## 5. 下一步（Codex 給的可執行方案）

### 5.1 先補能抓到缺陷的 XCUITest（**硬門檻：抓不到就不准開始第四次修復**）

- macOS 用 **`element.scroll(byDeltaX:deltaY:)`**，**不要**用 `swipe*` / `press(forDuration:thenDragTo:)`
  （Apple 明列後者為 iOS／Touch Bar 語義）
- **不再測孤立的 `CoverFlowStrip`**：加 `#if DEBUG` 的 `AZW_COVERFLOW_UI_TEST=1` 啟動模式，
  組裝真實 `RootView` ＋ `AppModel` ＋ `NowPlayingMonitor` ＋ `CoverFlowViewModel` ＋ `ArtworkService`，
  唯一替換可編程 `MusicControlling`；固定 20 項、ID `T00…T19`、20 張帶邊緣辨識色的 NSImage
- AX 探針：`CoverFlowStrip` 加 `.accessibilityIdentifier("coverflow-strip")`；
  centerLabel 加 `.accessibilityValue(model.centerID ?? "")`
- 三條測試：
  1. `testExternalScrollWritesBackAndDoesNotSnapBack`——滾動後回寫，且**不得被延遲 onChange 拉回或反向跳動**
     （記錄整段 ID 序列，斷言移動方向不中途反轉——這能抓第三次失敗的形態）
  2. `testKeyboardCommandsCanCenterBothEndpoints`——超量送方向鍵到兩端，
     `assertCardIsActuallyCentered` 必須同時斷言 `abs(card.midX − strip.midX) <= 3` 與長寬比≈1
     （只驗 label 抓不到缺陷 3 的「ID 正確但實際少滾三項」）
  3. `testCenteredCardPaintsAboveBothNeighbours`——用 AX frame 找重疊區取 5×5 像素，
     斷言呈現中心卡的辨識色（XCUIScreenshot 可直接取，不需 Screen Recording 權限）
- `waitForStableCenter()` 每 100ms 讀一次，連續四次相同才算落定；**不用固定長睡眠**
- 修好後跑 `-test-iterations 20`；最後仍需真實 20 張封面手滑一次
  （XCUITest 的 scroll event 不等價於實體觸控板慣性曲線）

### 5.2 修復方向

- **優先驗證移除共同根因 `.safeAreaPadding`**，而不是繼續給 zIndex 與 command 各打補償補丁。
  `.contentMargins(..., for: .scrollContent)` 是 SwiftUI 專門給 ScrollView 內容 inset 的 API，
  但**必須先讓新 UI 測試證明它真的修好**（本輪一個 agent 實測 contentMargins 失敗，
  但那是在無手滑測試的條件下測的，結論不可直接沿用）
- 架構上應拆分 `centerID` 的多重角色：`requestedCenterID`（一次性命令）／
  `settledCenterID`（實際落定）／`isUserScrolling`（來源與生命週期）；
  zIndex 從同一幀的實際幾何或 settled center 取得
- macOS 14 無 `ScrollPhase`（macOS 15+），但 AppKit 有明確標為 user-initiated 的
  `NSScrollView.willStartLiveScrollNotification`／`didEndLiveScrollNotification`，可經小型 bridge 使用

狀態：**v0.5 定稿（2026-10-27）**：v0.3 依附錄 A（Codex R1）改寫；v0.4／v0.5 依附錄 B（Codex R2、R3）修訂，R3 後無未決分歧。**使用者 2026-10-27 同意 §9 兩項，開工。**

## 0. 複述
使用者 2026-10-25：「歌詞有了時間軸，和真正唱的時候對得上對不上」是重要問題，之前沒被正面處理。
目標＝量清楚三種時間來源（內嵌 LRC／外部／估算）各自的「顯示起點 − 實際開唱」差多少、偏早還偏晚、多常顯示錯行，並用開工前寫死的決策表決定下一步攻哪裡。
完成標準＝§7 的數字全部填上、決策表給出唯一方向。不做＝任何改善實作、改來源鏈、改 app 的行為。

## 2. 事實（已核）
### 2.1 三種時間來源與它們在 app 裡怎麼接
- `TimingSource`（`Services/Lyrics/LyricsTimeline.swift:4`）：`embeddedLRC, lrclib, youtubeMusic, deezer, qq, netease, estimated`。
- **本機先建**：`LyricsTimelineBuilder.build`（`LyricsTimelineEstimator.swift:108`）——歌詞欄位是 LRC（`LRCParser.isLRC`）就用內嵌 LRC，顯示的是 **LRC 自己的行**；否則估算。
- **只有本機結果是估算時才查外部**（`LyricsFXViewModel.swift:163`：`timeline?.source == .estimated`）。→ 內嵌 LRC 組與外部組在 app 裡**互斥**；外部組的歌若沒找到，顯示的就是估算。
- **外部鏈**（`TimingResolver.lookup`，`TimingResolver.swift:370`）：依序問 LRCLIB → YouTube Music → Deezer → QQ → 網易雲，**第一個有候選通過 `LRCAligner` 的來源就勝出**、後面不問。整條鏈有 **20 s 時限**（`TimingResolver.swift:79`、`lookupWithinDeadline` `:319`）：到時取已通過的最佳候選，沒有就 `unavailable`；第 2 名以後的候選在開查 10 s 後不再開始（`extraCandidateCutoff` `:83`）。→ 後面的來源「單獨查得到」不等於 app 會走到它（R2 #5）。任一來源出錯且最終無人通過＝`unavailable`（不存檔、退避）；全部明確說沒有＝`notFound`（存 7 天）。
- **外部時間怎麼變成顯示起點**（`LRCAligner.timeline`，`LRCAligner.swift:76`／`:90`）：外部 LRC 對齊到 **Music 歌詞的行**；對上的行（錨點）用 LRC 時間，沒對上的行**線性內插**，頭尾以 `duration×0.06`／`×0.94` 為界（`interpolated`，`:161`）。→ 外部組要分「錨點行」「內插行」兩類量。
- **估算**（`LyricsTimelineEstimator.estimate`）：時間窗 `[duration×0.06, duration×0.94]`，行時長∝字數（下限 1.2 s），段落間隔 0.6 行、間奏標籤 3 行。不知道前奏與間奏的實際位置。
- 診斷事件（`TimingDiagnostics.swift`）已有逐來源的 `answer`（含對齊結果）／`noTiming`／`failure`，不含曲名與歌詞——量測工具沿用這組分類。
- 顯示起點＝`TimedLine.start`。進場動畫與逐字揭示（`revealEnd`）的時間差**不在本計劃**（附錄 A #14）。

## 3. 目標與非目標
目標（量測）：
- **M1 外部時間軸取得率**（嚴格對齊後，④ 之後）：200 首，先用 app 的 resolver 跑「鏈實際結果」（勝出來源／notFound→估算／unavailable），再對鏈沒問到的來源補查作診斷；每個來源分 found／明確沒有／暫時不可用（§4.5）。另記「差一點」：有候選但對齊沒過的筆數與其對齊率。
- **M2a 內嵌 LRC**、**M2b 外部（依來源分組，另分錨點行／內插行）**、**M3 估算**：逐行 signed error、早晚比例、錯行率（定義見 §4.3）。
- **M4 位置時鐘一致性**：app 的外推位置 vs Music 回報的 `player position`（不是演唱真值）。
- **可行性**：自動真值管線（＝日後「聽音訊自動校正」的核心技術）在這個曲庫上的可判定率、速度、離線性、授權、語言覆蓋。
- 依 §4.7 決策表（**本版寫死**）產出下一步方向。

非目標：改來源鏈或比對門檻、付費 API、改歌詞特效的畫法、逐字揭示的體感、任何進 Release 的改動、人工標註、Python 1.x。

## 4. 設計
### 4.1 樣本母體（開工前寫死）
- **快照 S0**（B0）：一次性 JXA 唯讀讀整庫 `persistentID`、`kind`、`duration`、`name`／`artist`（只在記憶體判版本標記，不落檔）、`lyrics`（只在記憶體算特徵，不落檔）。落檔只留：`persistentID`、時長、`hasLyrics`、`isLRC`、語言（`LyricsScript` 同規則：ja／非 ja）、歌詞行數、每分鐘行數、排除原因。快照時刻寫進檔頭。
- **母體 U**＝有詞（`LyricsStatus.present` 同規則）且：
  - 排除：影片（`kind` 含 video，A0 的 18 首）、時長 < 60 s 或 > 900 s、標題帶 live／版本標記（沿用 `TrackMatcher` 的版本標記表；Codex R1 #8）、純音樂／無詞。
- **E**＝U ∩ `isLRC`（內嵌 LRC 組）；**N**＝U ∩ ¬`isLRC`（會走外部鏈，查不到就是估算）。
- **M1 樣本**（R2 #9，寫死）：從 N 抽 200 首。
  - 層＝語言 {ja, 非 ja} × 每分鐘行數三分位（三分位點以 N 全體算）＝6 層。
  - 配額：200 先依語言按 N 中比例分，每種語言下限 50；語言內按三分位層的大小比例分，取整用最大餘數法。
  - 抽法：每首鍵＝SHA-256(`"20261027:" + persistentID`)，層內依鍵遞增取前 k 首。（名額按層大小比例分，不會超過層的首數，因此沒有補額步驟；實作見 `timing_probe_metrics.stratified_sample`。）
  - S0 快照檔的 SHA-256 與抽中清單的 SHA-256 記進附錄。
- **真值樣本**（B4）：
  - 外部：從 M1 樣本中，每個「查得到」的來源各抽至多 15 首（依同一把鍵遞增；不足就全取；同一首可同時供多個來源比較）。**鏈實際勝出**的曲優先入選，使 pooled 外部組反映 app 實際顯示的來源。
  - 估算：**N 組每首都算得出估算時間軸**，所以凡進真值的 N 組曲目都同時量 M3（成對比較，不另抽）；另從 M1 中「全部沒找到」的曲補到估算組合計 ≥ 20 首。
  - 內嵌：從 E 抽 20 首（同 seed；E < 20 全取）。
  - 預期總量 50–80 首。真值無法判定的曲不補抽（避免挑容易的歌）；整首被排除的曲進樣本流向圖與分母（R2 #17）。
  - **最低證據量**（R2 #8）：單一來源要下自己的結論需 ≥ 8 首可判定曲；pooled 外部、內嵌、估算各需 ≥ 20 首。不足＝該格輸出「證據不足」。

### 4.2 三組的「顯示起點」怎麼算（全部用 app 自己的原始碼）
- 量測工具以 `swiftc` 直接編 app 的原始碼（同 ⑦ T0 做法）：`LRCParser`、`LyricsLines`、`LyricsTimelineBuilder`、`LyricsTimelineEstimator`、`LRCAligner`、`TimingResolver`、5 個 provider、`SourceGate`、`TrackMatcher`、`CandidateRanking`、`HTTPClient`。**不改 app 原始碼**。
- **替身白名單**（R2 #12）：只准替換 I/O 邊界——存檔（換記憶體版，不寫 app 的正式存檔）、診斷（換成記錄到量測檔的版本，事件型別不變）、曲目 metadata 來源（改由 S0＋記憶體提供）。判定邏輯、門檻、時限、來源順序、`TimingSwitches` 一律用原值（`allEnabled`）。
- **等價性檢查**（B1 前；不等＝停）：固定建置 commit SHA、`swiftc` 版本、編譯參數。
  1. 純函式：工具對自編合成輸入（不含真歌詞）的輸出，逐項等於既有 XCTest 對同一組函式斷言的值（`LyricsTimelineEstimatorTests`、`LRCAlignmentTests`、`TimingAlignmentTests`、`CandidateRankingTests`）。
  2. **resolver 整合**（R3 #12）：工具的組裝（記憶體存檔、量測用診斷）配上可控時鐘（`deadlineSleeper`／`clock` 本來就可注入）與假 provider，跑：found、notFound、failure→unavailable、20 s 時限取快照、10 s 候選截止、來源未到達、各診斷事件。每個情境的結果與事件序列等於 `TimingResolverTests` 對同情境的斷言。
- E：`LyricsTimelineBuilder.build` 的行起點（LRC 行）。
- 外部（每個來源各一份）：該來源勝出候選的 `lineStarts` → `LRCAligner.timeline` 的行起點；每行標 `anchored`（有錨點）或 `interpolated`。
- 估算：`LyricsTimelineEstimator.estimate` 的行起點。

### 4.3 指標（逐行 → 逐首 → 彙總）
- **評估單位**：E 組＝內嵌 LRC 的行；外部與估算＝Music 歌詞的行。三組分行粒度不同，**逐行數字不做跨組橫比**；跨組只比逐首的體驗指標（錯行率、MAEₜ），結果表標明各組的文字來源與行數分佈（R2 #10）。
- **signed error** e＝顯示起點 − 程式真值（正＝晚、負＝早），只算可判定的行。
- **準時**：|e| ≤ 0.3 s；**早**：e < −0.3 s；**晚**：e > +0.3 s；另附 |e| ≤ 1.0 s 的比例。每行有真值不確定度 uᵢ＝|Aᵢ − Bᵢ|／2；||e| − 0.3| ≤ uᵢ 的行另標「邊界」，報邊界佔比（R2 #4）。
- **錯行率**：只納入「行 i 與 i+1 都可判定」的行；觀察時刻 τᵢ＝真值ᵢ＋min(0.5 s, (真值ᵢ₊₁ − 真值ᵢ)/2)；該時刻顯示中的行（顯示起點 ≤ τᵢ 的最後一行）≠ i 即錯行。末行與相鄰不可判定的行排除，報排除比例（R2 #3）。
- **重複行**：正規化後與同首另一行相同、或 `LRCAligner.similarity` ≥ 0.8 的行標「重複」；主分析含重複行，另報「排除重複行」的敏感度結果（R2 #11）。
- **逐首**：MAEₜ＝|e| 中位數；offsetₜ＝e 中位數；residₜ＝|e − offsetₜ| 的 P90；錯行率ₜ；首行 e 另記（前奏誤差）；中後段（後 2/3 的行）殘差另記。
- **彙總（寫死）**：**主結論一律每首等權**（先逐首、再跨首）：MAEₜ 中位數／P90、早／準／晚比例（先逐首算比例再取跨首平均）、錯行率ₜ 平均。每行等權的合併結果只放敏感度表，不進決策表（R2 #14）。外部組再按來源、錨點／內插分開報。
- **不確定性**：每個進決策表的比例與中位數報 bootstrap 95 % 區間（以曲為單位重抽 2,000 次，seed＝20261027）（R2 #8）。
- **曲庫加權**：依 S0 比例與 B1 的鏈實際結果，算「曲庫期望錯行率」＝Σ 組佔比 × 該組錯行率ₜ 平均。這是決策表排序的共同單位（§4.7）。

### 4.4 真值：程式聽音檔（Codex 執行）
- **取音檔路徑**（§9-1）：一次性 JXA 唯讀腳本，**只對已入選的樣本曲**讀 `location`（同 A0 做法，**不改 app、不改白名單**）；路徑只在記憶體、不落檔、不出程序，暫存檔跑完即刪。首次執行可能跳 Music 的自動化授權框，執行前先告知使用者。
- **管線**（每首）：
  1. `ffmpeg` 解碼成 wav 到暫存資料夾（不在 iCloud 同步目錄），跑完即刪。
  2. **人聲分離**：Demucs（`htdemucs`）取 vocals。
  3. **方法 A（聲學 CTC 強制對齊）**：torchaudio `MMS_FA`；非拉丁文字先轉讀音（日文：漢字→假名→羅馬字，工具 B3 選定並記版本；其他：`uroman`）。
  4. **方法 B（Whisper 系）**：`stable-ts` 的 `align()`，把同一份歌詞對到 vocals（原文字直接送，不轉讀音）。
  5. **行起點**＝該行第一個對齊到的詞（token）的起點。A、B 兩法都給出且 |A − B| ≤ 0.3 s → 程式真值＝兩者平均；否則「無法判定」。
  6. 一首有 > 50 % 的行無法判定 → 整首「無法判定」，不進誤差統計，但進樣本流向圖與分母。
- **用語（R2 #1、#2）**：A、B 是「**不同對齊器、共享上游**」（同一份 vocals、同一份歌詞），不是完全獨立。真值一律稱「**程式真值（雙法共識）**」，所有誤差數字附可判定率與 §4.4 校準結果；不寫成「實際開唱」。
- **文字輸入**：N 組送 Music 歌詞的行（`LyricsLines` 解析後的 lyric 行）；E 組送 LRC 去掉時間戳後的行。歌詞只在本機處理，不外送。
- **真值管線自檢**：
  - 平移：5 首在開頭補 3.000 s 靜音，兩法的行起點都應平移 3.0 ± 0.05 s。
  - 決定性：3 首重跑，同一法結果差 ≤ 0.01 s。
  - 單調性：同一法的行起點非遞減。
  - **可疑共識**（R2 #2）：兩法一致、但落在 vocals 能量低於該曲 10 百分位的區段，或早於前一行起點 → 標「可疑」，報佔比；可疑行不進主統計。
  - 各法單獨的失敗率（給不出時間的行比例）分開報。
- **外部校準（R2 #1，不需使用者標註）**：用公開、有人工時間標記的資料集，對整條管線量「程式真值 − 公開標記」。
  - **合格資料集（寫死，R3 新-1）**：人工標記的詞級或行級起點；音訊可取得；授權允許本機研究用途；≥ 20 首；至少涵蓋一種曲庫語言。行起點＝該行第一個詞的標記起點。候選：JamendoLyrics MultiLang（英、法、德、西；版本與授權 B3a 核，**TBD**）。
  - 每種語言分開報：|e| 中位數、|e| P90、signed e 中位數、可判定率。
  - **曲庫曲目的語言**（實施中補，附錄 C-1）：S0 只分 ja／其他；「其他」含校準集以外的語言。B4 以方法 B（Whisper）對 vocals 的語言偵測結果記每首語言，**只有偵測語言屬於通過校準的語言時才算已校準**。
  - **日文**：B3a 另查合格的日文資料集（**TBD**）。找不到 → 日文**沒有校準證據**，日文曲**排除出決策表與曲庫期望錯行率**，只在結果中描述性列出並標「未校準」（R3 #1）。
- **G0 值得擴跑閘**（B3 末；R2 #17：只決定「值不值得跑 B4」，**不是**全曲庫可行性結論）：
  1. 平移、決定性全過；
  2. B3a 找到至少一個合格資料集（找不到＝G0 未過），且其上程式真值的 `median(|e|)` ≤ 0.15 s、`P90(|e|)` ≤ 0.3 s、可判定行 ≥ 60 %；只有通過此項的語言能進決策表；
  3. 曲庫試跑 10 首（日文、非日文各 5）可判定行 ≥ 60 %。
  - 1、2 過、3 只有日文沒過 → B4 只跑非日文，日文標「無程式真值」；1 或 2 沒過 → 停在 B3，回報事實與替代方案。
- **可行性表**（附錄 A #11）：每種方法列語言覆蓋（ja／en／其他實測可判定率）、校準誤差、每首耗時（M4 Max）、是否全離線、授權（程式與模型權重分開列）、與另一法的差的分佈。授權未核前標 TBD。

### 4.7 決策表（本版寫死；看結果後不得改門檻，要改須重新評審並記錄理由）
**步驟 1 依序過閘，第一個成立的就是輸出（互斥）**：
| 序 | 條件 | 輸出 |
|---|---|---|
| 1 | G0 未過（§4.4） | 停；回報可行性事實，自動校正路線暫不成立 |
| 2 | 鏈 found 曲數、估算組、內嵌組（若 E ≥ 20 首）任一低於 §4.1 最低證據量 | 「證據不足」：只擴樣，不立改善案 |
| 3 | 步驟 2 沒有任何候選觸發 | 「無行動」：不立改善案 |
| 4 | 否則 | 步驟 2 觸發、且**可回收量 > 0** 的候選中最大者；若 (最大 − 次大)／最大 < 20 % → 兩者並列交使用者拍板。觸發但可回收量 ≤ 0 的候選列為「不可回收」，不參與排序；全部 ≤ 0 → 輸出「無行動：證據顯示不可回收」 |

**步驟 2 候選（各自獨立判定，可同時觸發）**：
| # | 觸發條件（逐首指標，每首等權） | 方向 |
|---|---|---|
| X2 | 外部組 ≥ 25 % 曲 \|offsetₜ\| > 0.3 s 且 residₜ ≤ 0.5 s | 逐首偏移自動校正 |
| X3 | 外部組 ≥ 25 % 曲 residₜ > 1.0 s | 逐行亂：某來源佔這些曲 ≥ 60 % 且該來源證據足 → 降級該來源；否則逐行對齊 |
| X4 | 外部組內插行的 \|e\| P90 > 2 s 且內插行佔外部行 ≥ 20 % | 改內插策略（人聲區段界定頭尾） |
| E1 | 內嵌組套用 X2／X3 同門檻 | 同上，對象換成內嵌 LRC |
| S1 | 估算組 ≥ 50 % 曲 MAEₜ > 2.0 s，**或**估算組錯行率ₜ 平均 ≥ 30 %（R2 #18） | 首行 \|e\| 中位數 > 3 s 且中後段殘差中位數 ≤ 2 s → 「估算下限改善」（人聲區段）；否則「逐行強制對齊」 |
| C1 | 鏈 found 率 < 50 % 且「對齊未過、最佳對齊率 0.5–0.7」佔沒找到的 ≥ 20 % | 放寬比對另案評審 |

- **權重**（實施中補，附錄 C-2）：每首的 weight＝該曲代表的曲庫佔比（依 S0 分層母體／樣本數）；N 組曲目同時有外部與估算兩筆紀錄時，**不是 app 實際顯示的那一筆 weight 給 0**——觸發條件與錯行率用全部紀錄，曲庫佔比只算實際顯示的。
- **可回收量**（共同單位＝曲庫期望錯行率的減少量；R2 #7、R3 #6／#7）＝ w(T) × mean(錯行率ₜ, t∈T) − w(T) × 目標錯行率；本計劃目標錯行率一律取 0（上限估計），C1 除外。各候選的曲集合 T 寫死：
  - X2：外部組中 \|offsetₜ\| > 0.3 s 且 residₜ ≤ 0.5 s 的曲。
  - X3：外部組中 residₜ > 1.0 s 的曲（降級來源時只取該來源的曲）。
  - X4：外部組中有內插行、且其內插行 \|e\| 中位數 > 2 s 的曲；錯行率只用其**內插行**算。
  - E1：內嵌組中符合 X2 或 X3 條件的曲（方向隨所觸發者）。
  - S1：估算組中 MAEₜ > 2.0 s 或錯行率ₜ ≥ 30 % 的曲。
  - C1：鏈沒找到、且有「對齊未過、最佳對齊率 0.5–0.7」的曲；可回收量＝w(T) ×（這些曲的估算錯行率ₜ 平均 − 外部組錯行率ₜ 平均），**可為負**。
  - w(T)＝T 的曲以 S0 分層權重推到曲庫的佔比（只計已校準語言）。
  - **重疊**：同一首可屬多個 T；各候選的可回收量各自計算、不去重（它們是互相替代的方向，不是相加的計畫），並列出兩兩重疊曲數供參考。
  - B2 的輸入／輸出把每個候選序列化為 `{id, triggered, track_set, weight, recoverable, rank}`；測試覆蓋可回收量為零、負值、並列、全部 ≤ 0、與重疊。
- X1（外部已準）不再是候選，只作描述：外部組 ≥ 80 % 曲 MAEₜ ≤ 0.3 s 時在結論寫「外部時間本身已準」。
- 門檻依據：0.3 s＝真值容差；2 s／3 s／30 % 為「一句歌詞明顯錯位」的量級（**推測**，B5 附分佈圖供使用者判讀，但不據此改門檻）。
- B2 的決策程式以合成資料覆蓋上表每一列、每個閘與並列分支。

## 8. 風險
- **真值錯誤相關**：兩法一起錯的行會被當成可判定。緩解：自檢＋結論附可判定率；B5 另報兩法差的分佈。
- **日文對齊品質**：方法 A 需漢字讀音轉換，讀錯會拉低可判定率（**推測**）；日文也沒有已知的公開校準集。B3 分語言報；日文過不了 G0 第 3 項時標「無程式真值」，**不**改用單一方法的結果充當真值。
- **真值只是雙法共識**：校準集只涵蓋部分語言與曲風，校準結果外推到本曲庫是**推測**；結論一律附可判定率、可疑行佔比與校準範圍。
